# Raon-1-mini 일반 9비트 bfp16ebs8 GEMV 커널 및 NPU 실행 명세

본 디렉토리는 AMD XDNA 2 AIE2P (Ryzen AI 7 350, 32 코어: 8열 × 4행) 상에서 사용자 결정(10-28) D 방식의 비-Q4_K 가중치 투영 행렬을 처리하기 위한 **9비트 bfp16ebs8 GEMV 커널**의 구현과 사양을 설명합니다.

---

## 1. 개요 및 산술 정확도 설계

### 1) 양자화 형식 (9비트 bfp16ebs8)
- 입력 $K$ 축 방향으로 8개 원소마다 1개의 공용 지수(1바이트 `uint8`, ebs8)와 8개의 가수(8바이트 `int8`)를 할당합니다.
- 오프라인 양자화 시 **최근접 짝수 반올림(conv_even / Round-to-Nearest-Even)** 을 적용합니다(`quantize_bfp16ebs8(..., rounding="conv_even")` 및 `bfp16ebs8_encode`).
- 공개 코덱은 mlir-aie와 같이 $e=0..6$도 보존합니다. 양의 가수가 128로 반올림되면 공유 지수를 1 올리고 블록을 다시 양자화하므로 평가 양자화와 패킹 값이 같습니다.
- 1개 블록(32행 × 256열)은 가수 8,192 B + 지수 1,024 B = **9,216 B**로 4바이트 정렬 및 16바이트 정렬을 완벽하게 만족합니다.

### 2) 산술 파이프라인 (Narrowing 오차 없는 정확한 누산)
- **가수 변환의 정확성**: int8 가수($|m| \le 128$)는 부호 1비트 + 7비트 정수이므로, bfloat16의 7비트 가수(fraction) 필드에 정밀도 손실 없이 **100% 정확하게(exact)** 변환됩니다.
- **스케일 곱의 정확성**: NPU 패킹 단계(`pack_bfp16_gemv(..., flush_tiny=True)`)에서만 공유 지수 $e < 7$인 블록과 0 채움 블록을 0(가수 0, $e = 7$)으로 저장합니다. `return_stats=True`는 이때 내려진 비영 블록 수를 반환하며, 통계를 요청하지 않으면 손실 발생 시 경고합니다. 따라서 커널 입력의 지수는 $e \ge 7$을 만족합니다. 커널(`bfp16_gemv.cc`)은 16개 지수 바이트를 벡터로 읽어 방어적 `max(e, 7)` 적용 후 정상 bfloat16 지수 비트 `(e - 6) << 7`을 순수 벡터 연산(분기·스칼라 루프·memcpy 없음)으로 조립하여 bfloat16 벡터로 재해석합니다.
- **연산**: 가중치 $w = bf16(m) \times bf16(scale)$는 bfloat16에서 정확하며, 입력 $x(bf16)$와 곱해져 **float32 누산기(`accfloat`)** 에 더해집니다.
- 기존 q4nx 커널과 달리 **32개 묶음 내적을 bf16으로 좁히는(narrowing) 단계가 전혀 없어**, K 방향 리덕션 전 구간에서 좁히기 오차가 발생하지 않습니다.
- 최종 출력 $y$만 에필로그(`bfp16_gemv_epilogue`)에서 최근접 짝수(`conv_even`)로 bfloat16으로 좁혀집니다.

## 2. 블록 메모리 배치 구조 (Block Internal Layout)

1개 가중치 블록은 $M_{tile} = 32$ 행, $K_{tile} = 256$ 열을 담당하며, 총 **9,216 Bytes**입니다.
AIE2P의 16-lane 벡터 로드와 파이프라인에 최적화하여 16행 반쪽(Half) 단위로 배치됩니다.

```
+====================================================================================================+
|                              bfp16 GEMV Block (32 rows x 256 cols = 9,216 Bytes)                   |
+====================================================================================================+
| [Half 0] Rows 0..15 (4,608 Bytes)                                                                  |
|   +----------------------------------------------------------------------------------------------+ |
|   | Group 0 (K 0..7)     : Exp (16B, rows 0..15) | Mant (128B, 8 cols x 16 rows, col-major) = 144B| |
|   | Group 1 (K 8..15)    : Exp (16B, rows 0..15) | Mant (128B, 8 cols x 16 rows, col-major) = 144B| |
|   | ...                                                                                          | |
|   | Group 31 (K 248..255): Exp (16B, rows 0..15) | Mant (128B, 8 cols x 16 rows, col-major) = 144B| |
|   +----------------------------------------------------------------------------------------------+ |
|   Total Half 0: 32 groups x 144 Bytes = 4,608 Bytes                                                |
+----------------------------------------------------------------------------------------------------+
| [Half 1] Rows 16..31 (4,608 Bytes)                                                                 |
|   +----------------------------------------------------------------------------------------------+ |
|   | Group 0 (K 0..7)     : Exp (16B, rows 16..31)| Mant (128B, 8 cols x 16 rows, col-major) = 144B| |
|   | Group 1 (K 8..15)    : Exp (16B, rows 16..31)| Mant (128B, 8 cols x 16 rows, col-major) = 144B| |
|   | ...                                                                                          | |
|   | Group 31 (K 248..255): Exp (16B, rows 16..31)| Mant (128B, 8 cols x 16 rows, col-major) = 144B| |
|   +----------------------------------------------------------------------------------------------+ |
|   Total Half 1: 32 groups x 144 Bytes = 4,608 Bytes                                                |
+====================================================================================================+
```

### 블록 순서 (Block Ordering)
전체 행렬 내 블록 배치는 `pack_gemv`와 동일한 청크 인터리빙 순서를 따릅니다:
- 슬라이스(Slice) 크기: $rows \times M_{tile} = 4 \times 32 = 128$ 행
- 블록 인덱스: `((slice * k_blocks + k) * rows + row)`

## 3. AIE2P 코어당 L1 메모리 예산 분석 (64 KiB Budget)

AMD XDNA 2 AIE2P 코어 타일의 L1 데이터 메모리는 **64 KiB (65,536 Bytes)** 입니다.
가장 큰 $K$ 차원을 갖는 **Dense MLP down-projection ($K = 12,032$)** 에서의 예산 검증:

| 버퍼 / 요소 | 산정식 및 구성 | 할당 크기 (Bytes) | 크기 (KiB) |
|---|---|---|---|
| **입력 벡터 `x`** | $K \times 2$ Bytes (bfloat16, `ObjectFifo depth=1`) | $12,032 \times 2 = 24,064$ | 23.50 KiB |
| **가중치 `w`** | $M_{tile} \times K_{tile} \times \frac{9}{8} \times 2$ (`depth=2` Ping-Pong) | $9,216 \times 2 = 18,432$ | 18.00 KiB |
| **출력 벡터 `y`** | $M_{tile} \times 2 \times 2$ (`depth=2` Ping-Pong) | $32 \times 2 \times 2 = 128$ | 0.125 KiB |
| **누산기 `y_acc`** | $M_{tile} \times 4$ (float32 누산 버퍼) | $32 \times 4 = 128$ | 0.125 KiB |
| **열합 `sums`** | **제거됨** (bfp16은 minimum offset이 없어 prep/sums 불필요) | **0** | **0.00 KiB** |
| **코어 스택** | 컴파일러 측정치 기반 정적 스택 | 8,192 | 8.00 KiB |
| **총합 (Total L1)** | **코어당 최대 메모리 사용량** | **50,944 Bytes** | **49.75 KiB** |
| **여유 공간 (Margin)** | $65,536 - 50,944$ | **14,592 Bytes** | **14.25 KiB (22.3% 여유)** |

> [!NOTE]
> q4nx 커널에서 필요했던 `b_group_sums` 버퍼(K=12032 기준 752 B)와 `k_prep` 단계가 완전히 제거되어 L1 공간과 연산 사이클이 모두 절약됩니다.
